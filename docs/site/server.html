GameFrameX.Server — 服务端概览

Server/ 是 GameFrameX.Server 的快照（.NET 10，Apache-2.0，来源见 Server/PROVENANCE.md）：Actor 模型（TPL DataFlow）+ SuperSocket 多协议 + MongoDB 持久化 + 状态-组件-代理三层与零停机热更新。本仓库的唯一增量是 Server/Config/（Luban 生成的我们自己的配置库）。

.NET 10 · C# MongoDB · SuperSocket · protobuf-net Roslyn 分析器强制分层（GFX0001~14）

Agent 方法的调度行为由特性标注控制——这是 Actor 串行化的关键：

特性调度行为
[Service]（默认）进入该 Agent 的 Actor 消息队列串行执行（TPL DataFlow 无锁排队，天然免锁）
[ThreadSafe]跳过队列直接调用（方法自身保证线程安全时用）
[Discard]即发即弃（不等待结果）
[TimeOut(ms)]方法级超时

Roslyn 源码生成器自动生成 Agent 的 Actor 消息队列调度代码（GameFrameX.Hotfix.WrapperGenerator）；Architecture.Analyzers 在编译期强制：State/Component 定义在 Apps 层、Handler/EventListener/ComponentAgent 定义在 Hotfix 层、命名后缀约定、Handler 必须 sealed（GFX0001~GFX0014）。

7 深读：背包全链路的真实代码

上游快照内置了完整可参照的背包实现。三层各是什么样子（均为真实源码摘录，去掉版权头）：

// ① 状态层（GameFrameX.Apps/Player/Bag/Entity/BagState.cs）——只有数据，MongoDB 透明持久化
public sealed class BagState : CacheState
{
    public Dictionary<int, BagItemState> List { get; set; } = new();
}
public sealed class BagItemState
{
    public long ItemId { get; set; }
    public long Count { get; set; }
}

// ② 组件外壳（.../Component/BagComponent.cs）——标记归属哪个 Actor 类型，两行完事
[ComponentType(GlobalConst.ActorTypePlayer)]
public sealed class BagComponent : StateComponent<BagState> { }

// ③ 业务代理（GameFrameX.Hotfix/Logic/Player/Bag/BagComponentAgent.cs）——热更层
public class BagComponentAgent : StateComponentAgent<BagComponent, BagState>
{
    public async Task<BagState> UpdateChanged(INetWorkChannel netWorkChannel, Dictionary<int, long> itemDic)
    {
        var bagState = OwnerComponent.State;                     // 直接摸状态
        var notify = new NotifyBagInfoChanged();                 // 组推送
        foreach (var item in itemDic)
        {
            if (bagState.List.TryGetValue(item.Key, out var value)) value.Count += item.Value;
            else bagState.List[item.Key] = new BagItemState() { Count = item.Value, ItemId = item.Key };
            /* ... 组 NotifyBagItem（含变化量与总量） ... */
        }
        // netWorkChannel 为空表示离线发放（统一奖励发放接口）：只持久化，不推送
        if (netWorkChannel != null) await netWorkChannel.WriteAsync(notify);
        await OwnerComponent.WriteStateAsync();                  // ★ 状态落盘（CacheState → MongoDB）
        return bagState;
    }
}
一次业务变更的固定节奏：改 State → 组 Notify 推送 → WriteStateAsync 持久化；配置校验也有真实样例（OnRemoveBagItem 里 ConfigComponent.Instance.GetConfig<TbItemConfig>().TryGet(...) 对 TbItem 校验）

消息怎么进到代理——Handler 壳用泛型五件套把"消息→组件→代理"静态接起来（编译期即可追），自己只包 try/catch：

// GameFrameX.Hotfix/Logic/Player/Bag/ReqAddItemHandler.cs
internal sealed class ReqAddItemHandler : PlayerRpcComponentHandler<BagComponentAgent, ReqAddItem, RespAddItem>
{
    protected override async Task ActionAsync(ReqAddItem request, RespAddItem response)
    {
        try { await ComponentAgent.OnAddBagItem(NetWorkChannel, request, response); }
        catch (Exception e) { /* 统一错误处理 */ }
    }
}

7.2 编译期分层：GFX0001~GFX0014

GameFrameX.Architecture.Analyzers（netstandard2.0 Roslyn 分析器，以 analyzer 引用挂在 Apps/Hotfix/Launcher 上）共 14 条规则，按分析器类名覆盖六类约束：CacheStateAssembly（State 必须在 Apps）、ComponentAgentAssembly / ComponentAgentName（代理必须在 Hotfix + 命名后缀）、EventListenerAssembly / EventListenerName / EventListenerSealed、HotfixBridgeAssembly、HttpHandlerAssembly 等——"状态在 Apps、逻辑在 Hotfix"不是口头约定，是编译错误。这也解释了为什么 10 章实战里服务端落位表那样划分。
